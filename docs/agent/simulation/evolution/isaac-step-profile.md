# 原厂IK之后的完整控制步耗时

2026-11-24，用户继续追问原厂IK已低于1 ms，为何step RPC仍约97 ms。本阶段对同一WG-r10＋OM-r08输入、原厂IK、20个5 ms物理子步、真实RTX双RGB、正常种子91000逐段计时，并逐项验证改动。没有重训BC／RL。

## 测量方法和基线

独立源码快照中用`perf_counter`记录调用次数及耗时。仅一个Isaac实例串行运行；每组正常回合388步，统计排除最初10步。worker总计时不含诊断日志自身落盘；step RPC另外包含客户端接收／解包。各嵌套计时为包含子调用的时间，不能把全部行直接相加。训练示范客户端的压缩／持久化在RPC之后，不包含在这里的单步时间中。

新基线实测step RPC均值96.195 ms，worker内部93.930 ms。主要构成：

| 路径 | 每步均值 | 调用次数与原因 |
| --- | --- | --- |
| `DirectWorld.render` | 40.867 ms | 一次同步Replicator调用，要求两个RTX子帧；包含内部USD同步 |
| 物理循环 | 24.727 ms | 20次目标插值、simulate／fetch及逐步胶垫／接触监测 |
| 接触／几何测量 | 14.194 ms | 一次任务测量＋两次奖励势函数额外测量；8对盒子重复成24次SAT |
| 取图／采样／缩放 | 7.472 ms | GPU图像取回、整图转float64、鱼眼ROI双线性采样和head缩放 |
| 其余 | 约8.9 ms | IK、历史构造、USD同步、RPC序列化／发送／解包、审计等 |

物理循环中的`simulate`均值2.456 ms、`fetch_results`19.590 ms；后者包含引擎完成／同步等待，不能解读为纯Python计算或纯求解时间。接触测量内的盒体SAT均值11.56 ms左右。串行API开销和重复的小数组运算都存在，不能把这些时间统称为GPU仿真耗时。

渲染使用本机Isaac 5.1的`omni.replicator.core/scripts/orchestrator.py::step`，内部驱动Kit `app.update()`，按子帧要求推进并等待当前图像完成；所以40 ms不是纯粹的两个小图GPU着色时间。这里没有人为等待100 ms来模拟控制周期；100 ms是20次5 ms物理推进的仿真时间。

## 已修复的重复计算

`isaac_rl_worker.py`的奖励势函数复用当前状态的已测位置／角度：步前使用上次返回状态，步后使用本次`env.step`测量。reset建立首个状态；每次渲染都断言q／dq未变。因此不再为奖励额外重做碰撞几何检查，且不用重新计算未参与位置势函数的旋转误差。TCP位置与姿态也从同一次查询取得。

`box_overlap.py`保留原15条SAT轴、轴顺序、近零阈值及公式，改用一次批量叉乘和范数运算，去掉大量小向量Python循环。2000组随机／近乎平行盒体与旧标量实现对照到小数点后10位mm，另有接触／分离／旋转角点测试。

腕部图像不再把整张512×512 RGB转为float64后再取128×128 ROI；原uint8数据直接与float64采样权重相乘，保留原插值／舍入顺序。独立RGBA非连续视图测试49152个输出值逐值相同。

仅以上改动，保持双子帧及默认物理线程，正常回合worker内耗时降到79.854 ms；其中测量降到1.860 ms、SAT到0.837 ms，奖励势函数约0.033 ms。正常388步逐步核对关节目标／实测关节／TCP／深度／角度／奖励／接触指标差均为0。真实RTX跨进程渲染本身有小幅像素差异，不能把两个独立运行的RGB声明为逐像素等价；采样公式的等价性由同一输入的单独检查证明。

这组优化的完整RPC为82.299 ms。正常、+1 mm恢复、−1 mm恢复分别388／573／576步通过；三例全部逐步比较上述字段与原厂IK原始运行一致，成功／失败／截断与恢复状态也一致。

## 未使用的默认预览视口

本机`SimulationApp`默认`headless=True`并不关闭预览更新，仍存在启用中的1280×720视口；实际policy只消费单独创建的256×256 head与512×512 wrist render products，再缩放／采样成128×128。只关闭预览、保留两个传感器的渲染，正常388步仍成功且物理状态／奖励逐步相同；渲染40.867→26.227 ms，RPC96.195→80.796 ms。

关闭时序很重要：在`SimulationApp(disable_viewport_updates=True)`启动时关闭的第一次实验，停在场景初始化阶段，监督器判定启动失败后以SIGTERM结束（退出−15）；未产生控制步，不能计入成功或计时均值。原日志与回执保留。改为场景、render products和三次预热都完成后，通过`get_active_viewport().updates_enabled=False`关闭，启动及闭环完成。仅凭现有日志不能精确定位第一次初始化等待发生在哪个内部函数。

生产worker现在采用后者，继续保留20子步、8个默认物理工作线程、原两个相机及双RTX子帧。`render_runtime`记录实际预览状态；新执行合同新增`render_runtime.version=headless-sensors-only-v1`。关闭一个视口仍会影响GPU调度／渲染历史，因此不声称RGB逐值等价，也不把旧检查点和回放静默改成新配方。`--keep-preview-viewport`可恢复旧预览及旧执行合同字段布局；批量研究入口传递相同开关。

## 组合结果

最终组合保留原厂IK、20物理子步、双RTX子帧与8个默认物理线程，只合入重复计算修复、图像复制修复和初始化完成后关闭无用预览：

| 正常种子91000，排除最初10步 | 原基线 | 最终组合 |
| --- | --- | --- |
| step RPC均值 | 96.195 ms | 68.810 ms |
| worker内总计 | 93.930 ms | 66.419 ms |
| 渲染 | 40.867 ms | 26.860 ms |
| 物理循环 | 24.727 ms | 25.627 ms |
| 接触／几何测量 | 14.194 ms | 1.860 ms |
| 正常回合墙钟，含记录／不含启动 | 47.220 s | 36.429 s |

RPC耗时减少28.5%，吞吐约1.40倍；回合含数据压缩／持久化后总耗时减少约22.9%。物理参数没有改动，其小幅时间差属于独立运行测时差异。正常、±1 mm恢复3/3完成，步数388／573／576；与原厂IK原始三例逐步核对关节目标、关节实测、TCP、深度、角度、奖励、接触指标、终止及恢复状态全部一致。每组client、shutdown、worker正常退出0。

轻量全套74项：20通过、54可选依赖跳过；有numpy的环境另跑3项SAT测试（含2000组对照）全部通过。图像采样同输入检查另记，真实RTX跨运行像素差异与物理轨迹一致性分别报告。诊断快照不作为新训练数据；生产入口另作正常回合验证：388步成功，逐步物理／奖励一致，RPC均值70.682 ms、回合含记录36.942 s，client／shutdown／worker退出0，并确认新的渲染合同字段和视口关闭状态。约2 ms的独立运行波动不改变主要结论。

## 单变量诊断

物理工作线程设置原本为8。仅把`/persistent/physics/numThreads`设为0（在调用线程执行）后，物理循环24.727→20.692 ms、RPC96.195→91.643 ms。正常轨迹和奖励逐步相同；当前没有改变生产默认线程设置。这项收益约4 ms，不是整个剩余耗时的主要来源。

仅将RTX子帧2改1后，渲染40.867→31.870 ms、RPC96.195→87.813 ms，正常388步成功且物理轨迹／奖励相同。但启动后第一步腕部RGB相对基线平均绝对差约6.05/255、最大131/255；后续样本约0.7～1.2/255。较少子帧改变了图像收敛过程，不能把一次规则成功当作视觉策略等价验证。此设置只留在诊断快照，没有更改生产双子帧配方。

## 后续：只看CPU物理的完整采集周期

用户要求先回到CPU方案，解释一次完整控制周期为何仍慢。本次保留CPU PhysX、20子步、原厂IK、真实两路RGB、默认双渲染子帧及关闭无用预览，额外测量客户端规则决策和记录，不改变生产代码。正常种子91000仍388步成功；client／shutdown／worker退出0。

必须区分step RPC与外层采集周期。后者从一次teacher请求开始，到下一次teacher请求开始，包含决策、step、记录及循环整理。排除最初10步、详细cProfile区间51～100及相邻101，最后一步没有下次teacher所以不计，共326个完整周期：

| 顺序阶段 | 平均墙钟时间 |
| --- | --- |
| teacher决策RPC | 1.742 ms |
| step RPC | 64.976 ms |
| 客户端EpisodeSpool.append记录 | 23.575 ms |
| 循环整理等 | 0.321 ms |
| 完整规则采集周期 | 90.613 ms |

step内部：实际环境推进（含IK、20子步、同步、测量／判定）28.412 ms；两路图像捕获（含渲染及后处理）31.690 ms；其余为奖励势函数、状态整理和通信等。物理循环自身24.391 ms，20次fetch合计18.933 ms。图像捕获中的同步渲染25.347 ms、CPU重采样／缩放约4.908 ms。上述父子计时不能重复相加。

新增证据解释了外层阻塞：每周期平均4次`fsync`共16.499 ms，包含在23.575 ms的记录时间内；通常分别对应新图像帧归档与转移样本的文件／目录同步。压缩、哈希、组织数据等占余下约7.076 ms。当前客户端记录完成后才提出下一次动作，因此这部分直接加到端到端周期上。它未包含在此前约65～71 ms的step数字中，也不是物理计算。

50步详细cProfile显示`rep.orchestrator.step`共调用200次`omni.kit.app.update`，即每控制动作4次Kit更新，累计含回调约1.295 s。双渲染子帧并不等于一次轻量GPU画面调用；这条同步捕获路径驱动应用更新、渲染调度及数据完成检查。不能把4次应用更新直接写成4张传感器图像或4个渲染子帧。

cProfile中的socket `recv`总等待包含客户端记录后才发下一条请求的间隔，不能把该累计等待误报为网络传输瓶颈。用于墙钟汇总的样本已排除cProfile区间，保留额外计时器的少量开销；这轮规则控制没有运行BC推理。

运行时配置确认帧率限制关闭、焦点内外sleep均为0，没有人为等待100 ms。worker每step墙钟62.851 ms、主线程CPU时间54.560 ms、进程各线程CPU合计294.835 ms。后者可高于墙钟且含后台工作；CPU时间也可包含引擎自旋，不能直接解释成有效算法计算量。当前系统暴露16核Xeon Platinum 8368Q虚拟CPU，cgroup未观察到限流计数；仅凭虚拟化信息不能认定宿主机抢占或频率导致了延迟。

CPU方案的后续工作应优先研究如何将记录移出控制关键路径、在保证图像对应当前物理状态的前提下减少Kit更新负担，以及物理循环的原生调度／求解成本。本轮没有删减相机、子步或持久化保证，也没有把GPU／增加环境数作为这次单环境延迟问题的替代答案。

证据：`/data/shapeforge/runtime/runs/isaac_cpu_cycle_20261124`，包含三种时钟计时、客户端fsync与完整周期计时、cProfile原始数据及调用方、运行时设置、源码快照、RGB／逐步审计和进程回执。恢复入口见[清单](../../../../manifests/isaac_cpu_cycle_20261124.json)。
